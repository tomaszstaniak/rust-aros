# WebAssembly Text language-server port

Reference workload: upstream wasm-language-tools / wat_server 0.11.0 at
428f74da7fcb85d2fca9bd9828f5ff7434c19af8 (MIT):
https://github.com/g-plane/wasm-language-tools/tree/428f74da7fcb85d2fca9bd9828f5ff7434c19af8

This is an actual server with the upstream parser, Salsa analysis, diagnostics,
formatter, symbols and request worker threads. The port changes transport and
constructor registration; it does not replace language analysis with a fixture.

## Prepare and build

Export the exact upstream revision, retaining its Cargo.lock. prepare.py checks
the lock SHA-256 and the complete exported tree (sorted relative UTF-8 filename,
NUL, binary SHA-256 of contents for every regular file, excluding .git/target).
The destination must be new. Upstream and Cargo registry sources stay unchanged.

    python3 ports/wat-server/prepare.py UPSTREAM_EXPORT WORKSPACE
    export CARGO_HOME=YOUR_PRIVATE_CARGO_HOME
    export CARGO_TARGET_DIR=YOUR_PRIVATE_BUILD_DIRECTORY
    python3 ports/wat-server/build.py WORKSPACE --toolchain nightly

The pinned compiler used for acceptance is rustc 1.100.0-nightly
(0dfb098f3 2026-08-31); stable 1.95 cannot compile the current upstream
std::debug_assert_matches use. Populate the private Cargo cache first with
cargo +nightly fetch --locked in the upstream export. Builds are offline.

For x86_64 ABIv11, use a separate prepared workspace and target directory:

    python3 ports/wat-server/build.py WORKSPACE --toolchain YOUR_ISOLATED_AROS_TOOLCHAIN --aros

This uses the repository's generated aros-env.toml and x86_64-aros.json.
The isolated std toolchain must include the exec adapter and previous M3 fixes.
The application graph explicitly replaces libc 0.2.186 with this repository's
libc-aros 0.2.189. The pinned inventory 0.3.24 crate archive is verified against
the upstream lock checksum, extracted beside the workspace, and patched there.
No SDK, registry source, global toolchain or guest library is overwritten.

inventory's upstream constructor cfg omits AROS. Its function pointer otherwise
lands in ordinary data, and Salsa's first document query panics with an
unregistered ingredient. inventory-aros.patch selects .ctors only for x86_64
AROS, matching the tested GCC 10.5 constructor output. Arm64 constructor
registration is still unvalidated.

## Acceptance client

    cargo +nightly build --manifest-path std-groundwork/wat-lsp-acceptance/Cargo.toml --release
    PATH_TO_CLIENT PATH_TO_WAT_SERVER

For native compilation, run Cargo from std-groundwork/wat-lsp-acceptance and
supply the same inventory patch path generated by build.py:

    cargo +YOUR_ISOLATED_AROS_TOOLCHAIN build --release --offline \
      --config 'patch.crates-io.inventory.path="WORKSPACE-deps/inventory-0.3.24"'

Use an absolute dependency path. Cross builds intentionally adjust the
application lock resolution for the path patch; the committed client lock
contains the original registry inventory pin for host use.

The client checks pre-main inventory registration, initialize, invalid WAT
diagnostics, full document repair with a UTF-8 export name, diagnostic clearing,
real formatting edits applied with UTF-16 positions, symbols, shutdown, EOF,
child exit and a joined stderr reader. Results include the actual JSON traffic.
This controlled acceptance client blocks: a wedged peer requires the external
VM supervisor because native Child::kill is still unsupported.

## VM staging

    python3 ports/wat-server/stage.py SERVER CLIENT NEW_PAYLOAD_DIR --prefix UNIQUE_RUN

Reserve the matching v11 pool machine, stop → stage → start, then extract
POOLINPUT:PAYLOAD.ZIP to RAM:wl with UnZip output redirected to a file.
Inspect the unzip result, then Execute RAM:wl/run-tests. stage.py preserves
host mode 0755 and applies guest Protect +e before exec. Reports go to unique
RESULTS: filenames; binaries and work stay in RAM. Collect only while stopped.
Use a new destination and prefix for every run.

The DOS read workaround is explicit on both peers. This does not establish
ordinary buffered PIPE support, async readiness, filesystem watching, full
rust-analyzer support, a Zed port, v1 runtime, or arm64/Macaros runtime.

## Outstanding requests and cancellation boundary

The client also sends 16 mixed formatting/symbol requests before reading their
responses. It matches numeric IDs rather than arrival order and rejects
duplicates, unrequested IDs, error responses and missing results.

Build the separate deterministic engine probe with:

    python3 ports/wat-server/build.py WORKSPACE --toolchain nightly --cancellation-probe
    python3 ports/wat-server/build.py AROS_WORKSPACE --toolchain YOUR_ISOLATED_AROS_TOOLCHAIN --aros --cancellation-probe

The output binary is wat-cancellation-probe. Pass its native binary through
stage.py's optional --cancellation-probe argument. It runs after the regular
LSP session and writes a separate cancellation report and rc. On the current
panic=abort target it deliberately probes a process-aborting engine path:
dismiss the guest's abort requester before checking final rc and collecting.

The probe opens real WAT, confirms ordinary symbol analysis, clones the service,
sets its Salsa cancellation token before another symbol query, and checks
whether cancellation is caught. Host unwinding catches it and returns None.
This is an engine cancellation boundary test, not acceptance of LSP
$/cancelRequest timing or process-kill support. Keep their results separate.

## Experimental unwind profile

The explicit --aros --unwind option selects panic_unwind and forces unwind
tables for a separate build directory. It does not change the generated target
JSON, standard abort-profile builds, shared SDK or installed sysroots. Clear ambient RUSTFLAGS and CARGO_ENCODED_RUSTFLAGS;
the recipe rejects them for this profile because they can override its flags.

    CARGO_TARGET_DIR=PRIVATE_UNWIND_OUTPUT python3 ports/wat-server/build.py AROS_WORKSPACE \
      --toolchain YOUR_ISOLATED_AROS_TOOLCHAIN --aros --unwind --cancellation-probe
    CARGO_TARGET_DIR=PRIVATE_UNWIND_OUTPUT python3 ports/wat-server/build.py AROS_WORKSPACE \
      --toolchain YOUR_ISOLATED_AROS_TOOLCHAIN --aros --unwind

Build the independent std-groundwork/unwind-acceptance probe and supply
stage.py --unwind-probe PATH. Its separate rc precedes the real LSP session;
the engine cancellation probe remains a separate final result. Compare this
profile's native results with the recorded abort-profile rc20, rather than
inferring recovery from compilation.

## Interactive edit/cancel/recovery workload

wat-interactive-acceptance is a separate binary in the acceptance package:

    cargo +nightly build --manifest-path std-groundwork/wat-lsp-acceptance/Cargo.toml --release
    PATH_TO_INTERACTIVE_CLIENT PATH_TO_SERVER

Cross-build from the acceptance package with the existing AROS toolchain and
inventory patch config. Use the unwind-enabled WAT server. stage.py accepts
--interactive-client PATH and writes distinct interactive output/rc after the
baseline session, launching a new server process.

This client continuously drains stdout on one thread and stderr on another.
It opens a 1024-function valid WAT document, sends 12 symbol/cancelRequest/
didChange cycles (each three-frame group is encoded before write_all/flush), and accounts for every response and empty diagnostic
notification regardless of order. At least one nullable/cancelled result is required; all-normal completion
rejects the run as insufficient interruption coverage. The final query checks a fresh document's
first/last expected function names before shutdown, EOF, wait and both joins.

Coalescing preserves framing and reduces gaps between delivery of related
messages; it does not promise atomic writes or force a scheduling outcome.
The client-only sender refuses groups larger than three messages/1 MiB and
retains terminal write-failure state across cleanup.

The traffic log summarizes frames (method, ID, version, size, result/diagnostic
counts) without dumping every large document/symbol payload. A null response
or RequestCancelled error is allowed for the stressed requests; the counter is
labelled null_or_cancelled. It does not attribute each cancellation to an
explicit notification rather than a pending document write. The deterministic
engine probe supplies separate cancellation-mechanism evidence.

The 30-second receive deadline is diagnostic. Writes, wait and joins may still
need the external VM supervisor if a peer wedges; this is not process-kill or
hard-timeout acceptance. Shutdown happens after replies are accounted for;
shutdown with active outstanding work remains a separate case.

## Diagnostic request lifecycle trace

prepare.py --request-trace applies a separate diagnostic-only patch and copies
the owned request-trace module into a new disposable workspace. Build it with
the same explicit unwind profile. Pass --trace-requests to the server (the
interactive client forwards arguments after SERVER); stage.py --trace-requests
adds it only to the interactive session.

The trace stores at most 512 events and reports truncation. It dumps them to
stderr after the server loop ends: registration, worker start, query completion,
write success/error, token removal, cancellation lookup hit/miss, and
cancel_applied after the token has actually been set. A lookup hit alone is
not evidence that cancellation was applied before worker start.

Deferred output avoids per-event logging I/O, but mutexes, allocations and the
diagnostic build still perturb scheduling. Keep these results separate from
ordinary-server acceptance. The trace is not a runtime repair or a scheduling
guarantee.
